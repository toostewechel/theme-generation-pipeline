# The design.md generator, explained simply

## What is it?

A tool that turns this repo's design tokens into a small, tidy "theme card"
called a `design.md` file. That file is what the
[frontend-slides](https://github.com/zarazhangrui/frontend-slides) plugin reads
when it builds a slide deck, so: **tokens in → presentation theme out**.

Think of it like this: the token files are a giant paint warehouse with
hundreds of labeled buckets. A slide generator doesn't need the warehouse — it
needs a small tray with 8 paints, a few fonts, and a sticky note explaining
"the green is the star, use it once per slide." The generator packs that tray.

## What's in a design.md file?

Two halves, split on purpose:

1. **The top (YAML front matter)** — machine-readable values: 8 colors, 6 text
   styles, 3 corner radii, 5 spacing steps. This half is **generated by the
   CLI** and always has the same shape; only the values change per theme.
2. **The bottom (markdown prose)** — human-readable personality: "editorial
   confidence on a clean white page", which color plays which role, do's and
   don'ts. This half is **written by Claude** (via the `generate-design-md`
   skill) or by hand, because personality can't be computed from JSON.

The golden rule: **the CLI owns the top, people own the bottom.** Re-running
the CLI refreshes the values and leaves your prose untouched, byte for byte.

## How does it decide which tokens make the cut?

A fixed, hand-picked mapping in
[`src/designmd/mapping.ts`](../src/designmd/mapping.ts). For example:

- `colors.primary` ← `text-default` (the main ink)
- `colors.tertiary` ← `bg-brand-default` (the brand accent)
- `typography.h1` ← the `heading-3xl` text style
- `spacing.md` ← `space-400` (16px)

The mapping never changes between runs, so every client's design.md has the
same slots — only the values differ. A test (`mapping.test.ts`) fails loudly if
someone renames a token the mapping depends on.

Behind the scenes the generator reads `src/tokens/manifest.json`, picks the
right file for each mode (light or dark colors, small/medium/large/full radius),
follows every `{reference}` down to its final value, and converts it to what a
web page wants: hex colors, `px`, `rem`.

## How do I use it?

```bash
# See what would be generated (writes nothing)
npm run generate:design-md -- --name "Client A" --emit-context

# Write the file
npm run generate:design-md -- --name "Client A"            # themes/client-a.design.md
npm run generate:design-md -- --name "Client A" --mode dark # themes/client-a.dark.design.md
```

Or just ask Claude to use the **`generate-design-md` skill** — it runs the
confirm step, writes the file, and authors the prose grounded in the real
resolved values.

## The per-client story

`src/tokens/` holds exactly one theme at a time. So the flow for many clients
is:

1. Retheme the tokens for Client A (e.g. via the `generate-color-theme` skill).
2. Run the generator → `themes/client-a.design.md` is snapshotted.
3. Retheme for Client B, run again → `themes/client-b.design.md`.

The `themes/` folder is committed, so it grows into a little library of
presentation themes even though the token source keeps moving on.

## When something breaks

- **"Unresolved token reference" / a failing `mapping.test.ts`** — a token the
  mapping points at was renamed or removed. Fix the name in
  `src/designmd/mapping.ts`; don't hand-edit generated output.
- **Wrong values in the front matter** — the tokens are the source of truth;
  change the tokens (or the mapping) and re-run. Hand edits to the front
  matter get overwritten on the next run.
- **Want a fresh prose skeleton** — pass `--force` (this deletes the authored
  body, so be sure).
